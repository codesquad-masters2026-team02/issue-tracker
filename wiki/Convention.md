# Convention

## 브랜치 전략

Git Flow를 간소화하여 사용합니다.

```
main (배포 가능 상태)
 └── develop (개발 통합 브랜치)
      ├── feature/{issue-number}-{short-desc}  (새 기능)
      └── fix/{issue-number}-{short-desc}      (버그 수정)
```

| 브랜치 | 용도 | 예시 |
|--------|------|------|
| `main` | 배포 가능한 안정적인 코드 | |
| `develop` | 다음 출시를 위한 개발 코드 (기본 작업 브랜치) | |
| `feature/*` | 새로운 기능 개발 | `feature/12-login-api` |
| `fix/*` | 버그 수정 | `fix/15-db-connection` |

### 브랜치 규칙
- `develop`에 머지하려면 **최소 1명의 Approve** 필요
- 작업 전 반드시 이슈를 생성하고 자신을 Assign

## 커밋 컨벤션

[Karma 스타일](http://karma-runner.github.io/6.3/dev/git-commit-msg.html)을 따릅니다.

### 형식

```
{type}: {description} (#{issue-number})
```

### 타입

| 타입 | 설명 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `refactor` | 코드 리팩토링 (기능 변화 없음) |
| `test` | 테스트 코드 추가/수정 |
| `chore` | 빌드 업무 수정, 패키지 매니저 수정 |

### 예시

```
feat: 로그인 API JWT 검증 로직 추가 (#12)
fix: 이슈 필터링 시 페이징 오류 수정 (#25)
refactor: 공통 응답 래퍼 구조 개선 (#30)
```

## 이슈 템플릿

GitHub 이슈 생성 시 3가지 템플릿이 제공됩니다:

| 템플릿 | 접두사 | 라벨 |
|--------|--------|------|
| 기능 추가 | `[FEAT]` | `feature` |
| 버그 수정 | `[FIX]` | `bug` |
| Chore (설정/인프라) | `[CHORE]` | `chore` |

각 템플릿에는 다음 섹션이 포함됩니다:
- **Context (배경)**: 왜 필요한지
- **Acceptance Criteria (완료 조건)**: 체크리스트
- **Priority (우선순위)**: High / Medium / Low

> 빈 이슈 생성은 비활성화되어 있습니다. 반드시 템플릿을 사용해주세요.

## PR 템플릿

PR 생성 시 다음 양식이 자동으로 적용됩니다:

- **관련 이슈**: `Closes #번호`로 자동 연결
- **작업 내용**: 변경 사항 요약
- **체크리스트**: 커밋 컨벤션, 빌드/테스트, 문서 업데이트, 셀프 리뷰
- **리뷰어에게**: 중점 리뷰 요청 사항
- **스크린샷**: UI 변경 시 Before / After

## 그라운드 룰

1. **리뷰 없이는 머지하지 않기**: 모든 PR은 최소 1명 이상의 Approve 필요
2. **작업 전 이슈 생성**: 코드 작성 전 Project Board에 이슈 생성 + 자신을 Assign
3. **일일 스탠드업**: 어제 한 일, 오늘 할 일, 블로킹 요소 공유
4. **깨진 유리창 방치 금지**: 빌드 실패/심각한 에러 발견 시 즉시 팀에 공유

## 분업 원칙

- **API First Design**: Swagger 명세를 먼저 정의 → Mock API 제공 → 프론트/백엔드 병렬 작업
- **도메인 분리**: 충돌 최소화를 위해 도메인별로 분업
- **공통 모듈**: 전역 예외 처리, 공통 유틸 등은 프로젝트 초기에 짝 프로그래밍으로 구축
